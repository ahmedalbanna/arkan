You are tasked with refactoring the Arkan codebase to enforce strict Clean Architecture boundaries as defined in the project's `.dependency-cruiser.js` configuration.

## Current State

- **Modules:** 8 (`admin`, `ai`, `ai-content`, `billing`, `projects`, `rag`, `templates`, `users`)
- **Total dependencies analyzed:** 5145
- **Violations detected:** 287 (259 errors, 28 warnings)

The violations primarily involve:
1. **Domain layer importing from outer layers** (application, adapters, infrastructure).
2. **Application layer importing from adapters or infrastructure** (e.g., use cases directly importing concrete repositories or API clients).
3. **Adapters importing infrastructure directly** (e.g., controllers importing Drizzle repositories instead of receiving them via dependency injection).
4. **Cross‑module imports** where one module imports domain entities or utilities from another module directly, bypassing a shared public API.
5. **Modules importing from `src/app/`** (Next.js routes/pages), which violates the inward dependency rule.

## Goal

Achieve **zero errors** and **zero warnings** from `dependency-cruiser` while maintaining all existing functionality. The code must strictly follow the layered dependency flow:

```
adapters → application → domain ← infrastructure
```

- `domain/` must have **zero** dependencies on other layers or external frameworks.
- `application/` may depend **only** on `domain/` and shared utilities.
- `adapters/` may depend on `application/` and `domain/`, and may import `infrastructure/` **only** through dependency injection (not directly in the file body).
- `infrastructure/` may depend **only** on `domain/` (to implement interfaces) and external libraries.

## Refactoring Strategy & Priority

Execute the refactoring in **phases**, starting with the highest‑impact fixes.

### Phase 1: Fix Domain Layer Violations (Highest Priority)

**Pattern:** Domain files importing from `application/`, `adapters/`, or `infrastructure/`.

**Action:**
- For each domain file with an outer‑layer import, identify the **reason** (e.g., a domain entity using a use case type, or a repository interface importing a concrete implementation).
- **Solutions:**
  - Move the imported code **into** the domain layer if it truly belongs there (e.g., type definitions, pure functions).
  - Invert the dependency using an **interface**: define the interface in `domain/` and let the outer layer implement it.
  - Remove the import if it is unused or can be replaced with a more abstract type.

**Examples of expected fixes:**
- If `domain/Project.ts` imports `application/use-cases/CreateProjectUseCase`, extract the use case's input/output types into `domain/` or define a separate `ProjectService` interface in domain.
- If a repository interface `IProjectRepository` imports `infrastructure/DrizzleProjectRepository`, delete that import and rely on dependency inversion.

### Phase 2: Fix Application Layer Violations

**Pattern:** Use cases or application services importing from `adapters/` or `infrastructure/`.

**Action:**
- Application layer must **only** know about domain interfaces.
- **Solutions:**
  - Replace direct imports of concrete repositories/services with their domain interfaces (already defined in `domain/`).
  - For imports of utility functions (e.g., `randomId`, `cn`), move those utilities to a shared `src/shared/utils/` directory that is exempt from layer checks (update `.dependency-cruiser.js` to allow this shared folder to be imported anywhere).
  - If a use case currently creates its own dependencies, refactor to **accept them via constructor injection** (or function arguments) so the composition root can provide the concrete implementations.

**Example:**
```typescript
// BEFORE (violation)
import { DrizzleProjectRepository } from '../infrastructure/DrizzleProjectRepository';
export class GetProjectsUseCase {
  constructor() {
    this.repo = new DrizzleProjectRepository();
  }
}

// AFTER (compliant)
import { IProjectRepository } from '../domain/repositories/IProjectRepository';
export class GetProjectsUseCase {
  constructor(private readonly projectRepo: IProjectRepository) {}
}
```

### Phase 3: Adapters → Infrastructure Direct Imports (Warnings)

**Pattern:** Controllers, hooks, or API clients importing concrete infrastructure classes directly.

**Action:**
- Adapters should receive their dependencies (use cases, repositories, services) from a **composition root**.
- **Solutions:**
  - For **API routes** (`src/app/api/.../route.ts`), move the instantiation of concrete repositories and services into the route handler itself (or a factory function). The route acts as the composition root.
  - For **React hooks**, they should **not** instantiate infrastructure. Instead, they should call API endpoints (via `api-client` services) or accept pre‑instantiated services via React Context.
  - For **controllers**, ensure their constructors accept interfaces and that the instantiation happens in the route handler.

**Example (API route refactor):**
```typescript
// BEFORE (violation in controller)
import { DrizzleProjectRepository } from '../../infrastructure/DrizzleProjectRepository';
class ProjectController {
  constructor() {
    this.getProjectsUseCase = new GetProjectsUseCase(new DrizzleProjectRepository());
  }
}

// AFTER (compliant, composition in route)
// route.ts
const repo = new DrizzleProjectRepository();
const useCase = new GetProjectsUseCase(repo);
const controller = new ProjectController(useCase);
```

### Phase 4: Cross‑Module Imports

**Pattern:** Module A importing directly from Module B (e.g., `projects` importing `UserSchema` from `users/domain`).

**Action:**
- Create a **public API** for each module via a `index.ts` file in the module root that exports only what is safe to share.
- Update `.dependency-cruiser.js` to allow imports from `^src/modules/[^/]+/index.ts` only.
- **If schemas need to be shared** (e.g., `UserSchema` used in `Project`), consider extracting shared schemas to a separate `@shared/schemas` package or move the schema to a common location like `src/shared/schemas/`. For this refactoring, we can temporarily allow cross‑module schema imports as defined in the current cruiser config, but the long‑term goal is to minimize such coupling.

### Phase 5: No Imports from `src/app/`

**Pattern:** A module file importing from `src/app/` (e.g., a hook importing a page component).

**Action:**
- These are clear violations of the dependency direction. **Remove the import entirely**.
- If functionality is needed by the module, move that code into a shared location (e.g., `src/shared/ui/` for components, `src/shared/hooks/` for reusable hooks).

## Execution Guidelines for the Agent

1. **Run `npx depcruise src`** after every few changes to verify progress.
2. **Work on one module at a time** to reduce risk. Start with a smaller module like `templates` or `billing`.
3. **Preserve all existing functionality.** Do not change business logic; only reorganize imports and dependencies.
4. **Use explicit type imports** (`import type { ... }`) where possible to avoid runtime circular dependencies.
5. **Update barrel files** (`index.ts`) as needed to provide clean public interfaces.
6. **If unsure about a specific import**, ask for clarification before removing it.
